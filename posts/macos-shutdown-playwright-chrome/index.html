Incident review

一次 macOS 无法关机排障：孤儿 Playwright/Chrome 进程与生命周期修复

Chrome 的崩溃报告很多，但真正挡住关机的不是一次崩溃，而是一棵收到退出事件后仍未结束、已经失去父进程的自动化浏览器进程树。

ShiLong Li 2026-07-30 约 10 分钟阅读 macOS · Playwright
结论先行 macOS 的注销日志明确显示，系统在等待一个由 Playwright 启动的无头 Chrome。它确认收到了退出事件，却没有真正退出。精确清理 5 组自动化浏览器进程后，真实关机与重启均成功；随后把浏览器所有权、关闭超时、信号处理和定向兜底写进测试辅助层，并通过正常路径与故障注入验证零残留。
5组失去原父进程的自动化浏览器
25个浏览器主进程与辅助进程
45份数日内累计的 Chrome 系列崩溃报告

依据注销日志 · 诊断报告

现象：关机卡住，Chrome 又频繁报错

最初看到的表象很像“Chrome 崩溃导致 macOS 无法关机”：点击关机后系统迟迟不结束，同时系统里又留有多份 Chrome、Chrome for Testing 和无头 Chromium 的诊断报告。

但这两件事不能直接画等号。判断关机阻塞，要看注销状态机当时在等谁；判断崩溃，要看诊断报告里的实际事件时间与调用栈。把两类证据分开后，问题才变得清楚。

关键证据与它能支持的结论
证据 观察 能支持的结论
进程树与完整命令行 5 组自动化浏览器共 25 个进程，主进程的原父进程均已消失，使用独立临时 profile 它们是遗留的自动化会话，不是日常 Chrome 标签页
macOS 注销日志 同一个无头 Chrome 收到退出事件并回复，但随后仍处于运行状态；多轮关机都在等待它 这是本次关机失败的直接近因

依据进程树 · 完整命令行

根因链：启动成功，不代表生命周期完整

还原命令行与调用关系后，可以得到一条有证据支撑的故障链：

  1. 一次本地 UI 自动化任务直接启动了系统安装的 Google Chrome，并为它创建临时 Playwright profile。
  2. 上层 Node 进程在异常或挂起路径中退出，没有完成浏览器关闭，也没有留下仍能负责回收的所有者。
  3. 浏览器主进程被系统接管，连同辅助进程持续存活超过两天。
  4. macOS 关机时向它发送退出事件；进程回复了系统，却没有结束。
  5. 注销状态机持续等待，因此用户看到的是“关机指令没有执行完”。

这里最值得修的不是某一个进程号，而是所有权丢失：谁启动浏览器，谁必须能在正常结束、抛错、收到信号、整体超时和优雅关闭卡住时把它回收。

另一个风险是把自动化指向日常使用的 Chrome。Playwright 官方文档也提醒：它与随包提供的浏览器配合最好，替换 executablePath 应当格外谨慎；自动化默认 Chrome profile 也不受支持。这个原则与本次事故的隔离需求一致。

结果25 进程归零

处置：只清理已证实的进程树

现场清理没有使用 killall Chrome 或模糊的 pkill -f。目标通过三项条件共同确认：自动化启动参数、Playwright 临时 profile、以及完整的父子进程树。先对 5 个主进程发送正常终止信号；确认它们没有退出后，才对这 5 棵已知进程树做定向强制终止。

结果是 25 个相关进程全部消失，日常 Chrome 与正式 profile 未被修改。LaunchServices 不再保留对应的活跃登记，随后一次真实关机走过 LogoutComplete 并进入系统 shutdown 状态机；机器重启后也没有恢复这些残留进程。

依据Playwright 官方 API

永久修复：有界关闭、明确信号、零残留验收

修复只落在 UI 测试的浏览器启动与关闭边界，没有改产品核心逻辑，也没有改依赖清单。测试辅助层采用 Playwright 管理的浏览器，并拒绝把配置指向日常 Google Chrome 应用。

1. 保留一个可强制回收的公开句柄

普通 chromium.launch() 返回浏览器对象；这里改用 launchServer()，同时持有 BrowserServer 与它的进程句柄。这样即使协议层关闭卡住，调用方仍可通过 Playwright 的公开 API 定向终止这一会话。

const server = await chromium.launchServer({
  headless: true,
  host: '127.0.0.1',
  handleSIGHUP: false,
  handleSIGINT: false,
  handleSIGTERM: false,
});

const browser = await chromium.connect(server.wsEndpoint(), {
  timeout: 30_000,
});

try {
  await runUiChecks(browser);
} finally {
  const closed = await settleWithin(server.close(), 5_000);
  if (!closed && server.process()) {
    await server.kill();
  }
}

这段代码是公开文章用的简化版。实际实现还保证关闭操作幂等，并在连接失败时走同一条清理路径。server.kill() 只作用于当前 BrowserServer，不会按进程名误伤其他 Chrome。

2. 让调用方统一拥有信号与总超时

浏览器库的默认信号处理被关闭，由测试辅助层统一接管 SIGHUP、SIGINT 与 SIGTERM。每种信号都先触发有界清理，再保留标准退出码。整次 UI 任务另有 30 分钟上限，超时后返回 124，并走同样的定向回收。

3. 将“零残留”写进完成条件

测试成功并不只看断言是否通过。验收还包括：没有带本次运行标记的浏览器进程、没有临时 profile 被继续占用、没有 LaunchServices 活跃登记，也没有新增的相关诊断报告。

状态未证实

还不能下什么结论

这次证据足以确认“哪个进程直接挡住了关机”以及“生命周期修复能否避免残留”，但仍不足以把底层责任归给某一个组件：

  • 尚不能确定最初是哪一个异常路径首先遗失了浏览器所有权。
  • 尚不能证明问题根在 Playwright、Chromium、调用方清理逻辑，还是它们与 macOS 应用注册机制的交互。
  • 此前的 45 次崩溃与两天后仍存活的孤儿进程可能相关，但没有证据证明它们来自同一个底层缺陷。
  • 一次受限执行环境内的浏览器探针因 Mach 端口权限产生了额外陷阱；同一探针在正常桌面环境通过，因此它被单独归类为环境边界问题。

修复范围只覆盖涉事本地项目的 UI 测试辅助层；它不代表上游 Playwright 或所有其他自动化调用方已经修复。

产出排查清单

下次遇到类似问题，我会先做这五步

  1. 先看注销日志。确认系统在等待哪个应用，而不是根据弹窗猜根因。
  2. 再看进程所有权。核对父进程、启动时间、命令行与临时 profile，区分日常浏览器和自动化会话。
  3. 把崩溃报告按事件时间归档。文件修改时间只能说明文件被写过，不能代表故障刚发生。
  4. 精确终止。只处理已确认的自动化进程树，先正常终止，再在有证据时定向强制终止。
  5. 以真实关机收尾。进程数归零只是中间结果；最终要看到 logout、shutdown、重新启动和无残留回归。

最重要的工程教训很简单：自动化任务的“完成”必须包括它启动的外部进程已经被回收。只要浏览器生命周期仍是无限等待，测试断言全部通过也不能算真正结束。
